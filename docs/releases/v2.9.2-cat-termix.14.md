# Cat-Termix 2.9.2-cat-termix.14 — 更新器 ARM64 OCI 镜像身份校验

**尚未发布：** 本文件为候选版本记录。只有完整源码、原生双架构 Docker CI 及固定镜像晋升全通过，才可称为正式版本。

## 修复范围

本次只修复 `docker/updater/updater.mjs` 的 OCI 导入身份判断与「已是最新版本」判断，不合并 Termix 上游、不改变原版 `main`、不调整 AI / Agent / SSH 的业务逻辑。

- Docker `/images/load` 成功导入后，规范化的 Docker image ID 可能与下载的 OCI 配置摘要不相等。原逻辑把这种情况误报成 `Imported image ID mismatch`，并且可能在升级后不断提示仍有新版本。
- **保留而非删除安全校验：** 继续校验 OCI 配置的 SHA256，逐层校验压缩流的 SHA256、解压内容的 DiffID；Docker 导入后额外检查 image ID 结构、操作系统、架构、源码和 revision 等全部 OCI 标签，以及所有解压层 DiffID 的长度、数量、顺序与摘要。错误架构、标签、层或损坏内容必须拒绝。
- 新增模拟 Docker ID 规范化不一致的测试，并用真实 Docker 完成镜像导入；同时验证被篡改的层身份必须失败。CI 在 AMD64 和原生 ARM64 分别执行更新器真实导入及备份/回滚 smoke。
- 更新器内置版本 `VERSION = "2"`，可通过现有 `/control/status.json` 中的 `updaterVersion` 判定 sidecar 是否真正升级。
- 保留此前 v13 的 AI 多模型、Agent 安全和 SSH 功能；不增加数据表和账号迁移。

## 2244 服务器升级注意

**本次仓库发布不直接替换服务器容器。** 用户 2244 上已有可用的本地修复版更新器，请等 v14 双架构镜像验证完成后再在维护窗口替换。应用和独立 `cat-termix-updater` 虽然共享镜像标签，却是两个不同容器：软件内更新主应用并不会自动重建更新器 sidecar。

先备份数据卷，保存现有 Compose 与代理环境变量；确认 `CAT_TERMIX_IMAGE` 指向 v14 新镜像或原有 `ai-dev`；然后在原 Compose 项目目录执行：

```bash
docker compose -f docker-compose.ai-test.yml -f docker-compose.ai-updates.yml pull cat-termix-updater
docker compose -f docker-compose.ai-test.yml -f docker-compose.ai-updates.yml up -d --no-deps --force-recreate cat-termix-updater
```

仅替换更新器服务，不删除、重建数据库或数据卷，不执行 `down -v`；保留原来的 `COMPOSE_PROJECT_NAME`、代理、端口和挂载。重建后在 `cat-termix-update-control` 持久卷的 `status.json` 中观察 `updaterVersion: "2"` 和新 heartbeat。若 sidecar 无法启动/验证失败，应回退 v13 或恢复原服务器临时补丁，先排查再继续。真实 SSH、网络代理、用户账号与 2244 实例的业务验收仍需单独完成。
