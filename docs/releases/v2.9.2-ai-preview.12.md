## Agent 传输安全

`/agent/v1` 与 `/plugin-api/agent/v1` 使用实际 TCP 来源及 TLS listener 判断 HTTP 策略，不接受客户端伪造的 X-Forwarded-For / X-Forwarded-Proto 提升信任。Nginx 防护规则不区分大小写，并覆盖无尾随斜杠的前缀。核心公开路由匹配仍区分大小写：未登录请求访问 `/V1/` 时会先被认证层以 401 拒绝，不应错误要求这一安全拒绝必须是 426。管理员网页的会话、同源与权限校验保留。

每种架构都从容器外部完成 16 项传输检查：标准入口及无尾随斜杠入口拒绝未授权 HTTP，伪造协议、IPv4/IPv6 来源和 Forwarded 头不能放行；大小写别名仍拒绝未登录请求。容器内部的正常 Ed25519 配对、签名轮询和未授权访问拒绝检查也通过。

从反向代理终止 HTTPS 再用 HTTP 连接 Agent 的部署，仍需管理员明确配置实际代理来源的 LAN HTTP 策略，或让 Agent 流量在容器 TLS listener 上终止；不能用任意代理头替代授权。

## 新增主机与可编辑授权

设备选择“全部本人主机”时自动包含以后新增的本人主机。选择指定分类时，可勾选“包含所选分类中以后新增的主机”；不会跨到其他分类或其他用户的主机。旧版指定分类的授权继续保留其原先范围，升级不会静默扩权。需要继承新增主机的旧客户端，打开“本地 Agent → 编辑权限”，启用该选项后保存，无需重新配对。

已配对客户端可修改权限、主机分类、有效期和并发会话数，设备 ID 和密钥保持不变。新增权限用于后续请求；缩减权限会关闭该客户端已跟踪的 SSH 会话和租约，并取消可取消的任务，不会撤销已在远端完成的写入。

撤销会删除设备记录及关联配对、nonce 和幂等缓存，旧密钥随后被拒绝。旧版留下的已撤销记录不再显示，并在下一次状态持久化时清理；安全审计保留。

修复授权前置检查失败却遗留 pending 幂等记录、导致改权后安全重试误报 409 的情形。仅对能够确认尚未产生副作用的权限/目标检查失败释放记录；真正的请求冲突、写入租约冲突或远端执行结果不明仍保留 409 保护，不能把它们自动当作成功或重复执行。没有取得用户原始 409 响应或接入其服务器，因此不声称已经复现其所有 409 情形。

## 每个渠道启用多个模型

渠道配置新增模型勾选列表，支持搜索、全选、清空和手动添加模型 ID，最多 100 个。默认模型与启用模型列表分离；取消默认模型时改选剩余模型。聊天框按渠道显示全部已启用模型，同名模型仍使用各自渠道的配置。保存后刷新已打开的聊天模型菜单，无需重新添加渠道。

启用列表按用户和渠道保存于现有 AI 偏好数据，重启后保留，不包含 API Key。模型发现失败不丢失已保存的选择；显式清空表示禁用该渠道的所有模型，不会退回启用全部上游模型。尚未配置启用列表的旧渠道保留原兼容行为。模型、思考程度与审批偏好继续持久化。本轮不新增数据库表迁移。

## 测试部署注意

先备份现有数据，并在系统管理员设置中关闭“自动安装”。现有更新器继续跟踪 `ai-dev`，不会自动选择这个固定测试标签；测试期间保持自动安装关闭，避免它切回滚动渠道。沿用原 Compose 项目名、端口、卷及环境配置，仅将应用镜像改为上面的 `2.9.2-ai-preview.12`；不要删除数据卷，不要重新初始化账号。

若使用仓库提供的两个 Compose 文件，可在原部署目录、保留原环境变量的前提下运行：

```bash
export CAT_TERMIX_IMAGE=ghcr.io/luoquan0/cat-termix:2.9.2-ai-preview.12
docker compose -f docker-compose.ai-test.yml -f docker-compose.ai-updates.yml pull cat-termix
docker compose -f docker-compose.ai-test.yml -f docker-compose.ai-updates.yml up -d --no-deps cat-termix
```

上面的 export 只影响当前 shell；后续重建前应将该镜像选择保存到现有部署配置。只更新主应用，不要求重建或重启独立更新器。更新会断开现有 SSH 会话。自动化检查不等于已在用户真实 SSH/SFTP 主机和第三方模型账号下完成业务验收。
